# فروش و قیمت‌گذاری و پایش خطاها

## مسیرهای آماده

| مسیر | کاربرد |
|---|---|
| `/admin/pricing/rates` | تنظیم سرویس نوسان، کلید، فاصله دریافت، اعتبار نرخ، نرخ دستی و تاریخچه |
| `/admin/pricing/rules` | قاعده عمومی و محاسبه قیمت از وزن واقعی قطعه یا وزن آزمایشی |
| `/admin/pricing/discounts` | ایجاد و ویرایش تخفیف اجرت با بازه شمسی و پایان خودکار |
| `/admin/pricing/invoice` | لوگوی فروشگاه، متن پایین فاکتور، نمونه چاپی و ذخیره PDF از مرورگر |
| `/admin/settings/errors` | جستجوی خطا، فیلتر روز، نوع، صفحه‌بندی و جزئیات |
| هر مسیر ناموجود | صفحه اختصاصی ۴۰۴ با حفظ کد وضعیت HTTP |

تمام مسیرهای مدیریتی به نقش Administrator محدود شده‌اند. از کنار قطعات کاتالوگ نیز می‌توان محاسبه قیمت همان قطعه را باز کرد.

## راه‌اندازی نرخ

1. در «نرخ طلا» کلید اشتراک نوسان را وارد کنید. هیچ کلید پیش‌فرض یا آزمایشی در برنامه قرار ندارد.
2. واحد پاسخ تأمین‌کننده را پیش از اولین دریافت با قرارداد سرویس تطبیق دهید. ریال بر ۱۰ تقسیم می‌شود؛ نمایش و محاسبات داخلی تومان است. پس از اولین نرخ معتبر، تغییر واحد مسدود است تا سابقه‌های قبلی با تفسیر جدید مخلوط نشوند.
3. فاصله ۱، ۵ یا ۱۵ دقیقه و مدت اعتبار را تعیین کنید؛ اعتبار باید حداقل برابر فاصله دریافت باشد.
4. دریافت دستی را آزمایش و سپس دریافت خودکار را فعال کنید. آدرس اتصال ثابت و HTTPS است؛ پشتیبانی واقعی اشتراک و پاسخ سرویس باید با کلید فروشگاه بررسی شود.

کلید با ASP.NET Core Data Protection رمز می‌شود و در فرم بازنمایی نمی‌شود. هنگام انتقال نصب به سرور جدید، کلیدهای Data Protection نیز باید با روش امن همراه اطلاعات منتقل شوند؛ در غیر این صورت مدیر باید API key را مجدداً ثبت کند. لاگ URL درخواست برای HttpClient این Provider خاموش است چون API مورد استفاده کلید را در query string می‌پذیرد.

BackgroundService مستقل از باز بودن مرورگر، فاصله دریافت را رعایت می‌کند. درخواست‌های هم‌زمان در یک نمونه برنامه با قفل داخلی محدود می‌شوند؛ این MVP برای یک نمونه اجرایی است. هر پاسخ موفق یا ناموفق رکورد مجزا دارد. کش فقط آخرین نرخ معتبر API را نگه می‌دارد و پس از پاک شدن از دیتابیس بازیابی می‌شود. زمان دریافت و زمان منبع جدا هستند؛ پاسخ موفق با زمان منبع قدیمی، نرخ قابل استفاده محسوب نمی‌شود. نرخ دستی انقضای مستقل دارد و پس از انقضا، نرخ خودکار دوباره از نظر اعتبار بررسی می‌شود. صفحه باز هر ۱۵ ثانیه وضعیت نرخ را تازه می‌کند، بدون پاک کردن فرم در حال ویرایش.

## محاسبه نسخه اول

- دامنه: طلای ۱۸ عیار؛ وزن خالص طلا از قطعه کاتالوگ گرفته می‌شود. نرخ ۱۸ عیار نباید برای قطعه با عیار متفاوت استفاده شود.
- ارزش طلا = وزن × نرخ هر گرم.
- اجرت = درصد ارزش طلا، مبلغ هر گرم یا مبلغ ثابت قطعه.
- سود = درصدی از مجموع طلا و اجرت.
- تخفیف = بزرگ‌ترین تخفیف معتبر از اجرت، حداکثر به اندازه اجرت؛ تخفیف‌ها جمع نمی‌شوند.
- مالیات = درصدی از اجرت پس از تخفیف + سود. پیش‌فرض صفر است؛ این مبنا یک انتخاب پیاده‌سازی MVP است و تأیید انطباق مالیاتی نیست.
- مبلغ نهایی در آخرین مرحله گرد می‌شود و اختلاف گرد کردن نمایش داده می‌شود.

تخفیف در نسخه اول روی اجرت همه محصولات است. بازه از ابتدای روز شروع تا پایان روز انتخاب‌شده به وقت تهران است. هزینه سنگ، قواعد اختصاصی هر محصول، عیارهای دیگر و ارسال هنوز در این محاسبه نیستند. پیش‌نمایش فرضی با نرخ آزمایشی قابل استفاده است، اما گزینه نرخ زنده با نرخ نامعتبر محاسبه نمی‌کند.

فرم‌ها اعتبارسنجی سمت سرور دارند؛ تنظیمات و تخفیف‌ها با rowversion از بازنویسی هم‌زمان محافظت می‌شوند. تغییرات قیمت‌گذاری در OpLog همراه تغییر اصلی ثبت می‌شوند.

## مرز صورتحساب و سفارش

صفحه صورتحساب، قالب و پیش‌نمایش چاپی است. PDF از مقصد Save as PDF مرورگر دریافت می‌شود. نام، لوگو و نشانی از تنظیمات واقعی فروشگاه و ردیف خرید از داده فرضی می‌آید؛ برچسب نمونه در چاپ باقی می‌ماند.

پروژه فعلاً قابلیت سفارش و پرداخت ندارد. بنابراین در این مرحله صدور فاکتور واقعی، قفل قیمت پرداخت، snapshot فاکتور و اتصال مالیاتی پیاده نشده‌اند. هنگام افزودن سفارش باید وزن، نرخ، اجزای قیمت، تخفیف، نسخه قاعده و مشخصات فروشنده همان لحظه روی سفارش ذخیره شوند؛ محاسبه مجدد فاکتور قدیمی از تنظیمات امروز مجاز نیست.

## راهکار ثبت خطا

برای مقیاس فعلی، نیاز به سرویس خارجی یا زیرساخت جدا نیست:

1. Middleware استثنای درخواست HTTP و پاسخ صریح ۵۰۰ را ثبت می‌کند. استثنا دوباره به exception handler استاندارد ASP.NET Core تحویل داده می‌شود تا پاسخ عمومی، فاقد جزئیات فنی باشد.
2. ErrorBoundary در درخت تعاملی Blazor خطاهای کامپوننت‌ها را می‌گیرد. ILoggerProvider محدود نیز خطاهای CircuitHost و worker نرخ را ثبت می‌کند. خطای Blazor برچسب جدا دارد زیرا الزاماً HTTP 500 تولید نمی‌کند. خطاهای شروع برنامه نیز در فایل نوشته می‌شوند.
3. ابتدا رکورد با شناسه GUID در `App_Data/error-spool`، خارج از wwwroot، نوشته و روی دیسک flush می‌شود. سپس worker هر ۵ ثانیه آن را وارد SQL Server می‌کند. پس از commit، فایل حذف می‌شود. قطع دیتابیس فایل را نگه می‌دارد و تلاش بعدی آن را منتقل می‌کند. شناسه ثابت از ثبت دوباره پس از restart جلوگیری می‌کند. فایل موقت باقیمانده از توقف ناگهانی هم پس از یک دقیقه بررسی می‌شود.
4. فهرست از SQL، با فیلتر تاریخ و صفحه‌بندی سمت سرور خوانده می‌شود؛ Stack trace فقط هنگام باز کردن جزئیات بارگیری می‌شود. جستجوی متن روی پیام، Stack trace، نوع استثنا، مسیر و شناسه انجام می‌شود.

داده‌های ثبت‌شده: شناسه خطا و درخواست، UTC با میلی‌ثانیه، منبع، HTTP status در صورت وجود، message، نوع exception، زنجیره exception و stack trace، مسیر بدون query، روش درخواست، شناسه کاربر در صورت دسترس‌پذیری و محیط اجرا. زمان نمایشی تهران/شمسی است.

بدنه درخواست، headerها و cookieها ثبت نمی‌شوند. الگوهای معمول password، token، API key و queryهای URL از متن استثنا پوشانده می‌شوند. این پوشاندن تضمین تشخیص هر نوع داده شخصی در متن دلخواه نیست؛ در کد آینده نیز نباید اطلاعات محرمانه داخل exception نوشته شود. Razor متن خطا را escape می‌کند و آن را به HTML اجرایی تبدیل نمی‌کند.

## نگهداری و محدودیت‌ها

- حساب اجرای برنامه به پوشه صف خطا مجوز نوشتن نیاز دارد. در شکست هم‌زمان دیسک و دیتابیس، ذخیره پایدار تضمین‌پذیر نیست و پیام شکست ثبت در stderr نوشته می‌شود.
- خطاهای وب‌سرور/پراکسی پیش از ورود به برنامه، توقف سیستم‌عامل و خطاهای مرورگر خارج از Blazor در دامنه این ثبت نیستند. برای میزبانی نهایی، لاگ IIS/پراکسی و میزبان نیز باید نگهداری شود.
- حذف خودکار سابقه‌ها در MVP فعال نشده؛ مدت نگهداری را باید بر اساس نیاز فروشگاه و ظرفیت سرور تعیین کرد. دیتابیس و صف انتقال‌نیافته باید در سیاست پشتیبان‌گیری لحاظ شوند.
- این راهکار برای یک نصب و یک نمونه برنامه است. برای چند نمونه، صف مشترک/ثبت متمرکز و قفل زمان‌بندی توزیع‌شده لازم می‌شود.
- برای مقیاس بزرگ‌تر یا هشدار فوری می‌توان بعداً Serilog و Seq یا Sentry را ارزیابی کرد؛ اکنون وابستگی و هزینه خارجی اضافه نشده است.

## اعتبارسنجی

تست‌های واحد محاسبات اجرت، مبنای سود و مالیات، سقف و عدم ترکیب تخفیف، انقضا، گرد کردن، تبدیل ریال، زمان نرخ، ماندگاری فایل خطا، خطای HTTP صریح، لغو درخواست، حذف الگوهای محرمانه و تفکیک خطای Blazor را پوشش می‌دهند. تطابق migration با مدل نیز بدون اتصال دیتابیس تست می‌شود.

تست یکپارچه رسمی SQL Server طبق معماری باید در Docker اجرا شود؛ در این محیط Docker daemon در دسترس نبود. migration روی دیتابیس محلی برنامه اعمال شد و انتقال خطای واقعی به جدول ApplicationErrors مشاهده شد. اتصال واقعی Provider به کلید فروشگاه نیاز دارد و هنوز تأیید نشده است.

### بررسی رابط مدیریتی پس از ورود

- ورود حساب مدیر، بارگذاری صفحات نرخ، قواعد، تخفیف، قالب فاکتور و گزارش خطا در مرورگر تأیید شد.
- در پیش‌نمایش، اجرت ۵٪ برای دو گرم با نرخ فرضی ۱۰ میلیون تومان، اجرت یک میلیون و جمع ۲۱ میلیون را نمایش داد؛ این مقدار آزمایشی ذخیره نشد.
- ذخیره قاعده با مقادیر موجود در دیتابیس با پیام موفقیت تأیید شد.
- تخفیف ناقص با پیام اعتبارسنجی رد شد و رکورد آزمایشی ایجاد نشد.
- جستجوی خطا، کاهش نتایج به رکورد موردنظر و نمایش زمان میلی‌ثانیه‌ای UTC، Message و Stack trace واقعی بررسی شد.
- نمایش گزینه گرد کردن مبلغ پس از بارگیری decimal دیتابیس اصلاح و در مرورگر تأیید شد؛ ۴۰ تست پس از اصلاح نیز موفق بودند.
